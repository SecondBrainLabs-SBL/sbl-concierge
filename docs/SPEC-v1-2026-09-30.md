# Product specification — SBL AI CX Concierge

> Prepared 29 September 2026; revised 30 September 2026 after founder review (browser-first execution, Jev deferred, M7-only scenario thresholds). Genesis CLI state is authoritative for approval status. No deployment is authorized by this specification.

## Problem

SBL visitors and customers need contextual help that completes useful work across discovery, conversion, activation, support, retention and expansion. Evolve the existing extension prototype into a branded website-and-dashboard concierge, preserving working primitives where appropriate. The objective is verified customer outcomes rather than a chat-only tour.

## Users

New anonymous visitors, pricing evaluators, new signed-in customers, active campaign operators, returning/inactive customers, customers seeking support or cancellation, and SBL operators reviewing failures. Internal research workers serve the concierge; they are not external customer agents.

- `sbl-app` sources show billing routes and account-specific plan/usage logic, but no verified concierge quote-and-eligibility contract. A public price, observed account screen or frontend calculator is insufficient for an actionable offer. M1 must identify the exact scoped backend read and owner-approved offer facts.
- The app wiki reports existing revision checks and durable operation records for selected campaign actions, alongside skipped public-API contract tests and incomplete effect-tool live coverage. Treat this as a lead for targeted verification, not a passed gate. Use an approved non-production workspace and run-owned draft for read/create/readback proof; do not replay writes or use a production customer campaign to fill a proof gap.
- The founder confirmed that `sbl.so` is WordPress and that they own its deployment. An owner-installed custom JavaScript snippet or iframe is acceptable for the MVP; the embed must still receive only permitted page context and work without a visitor extension. The founder also clarified that “HumanLayer” means the in-house Genesis approval workflow, not a vendor integration. No non-production workspace has been designated yet; M1 can complete source/build checks while runtime write proof waits for a safe target.
- On 30 September, the founder clarified the order: develop advanced concierge capability on both `sbl.so` landing/pricing pages and the real SBL dashboard now through the existing Chrome extension. M1 starts with a grounded website answer, context/goal choice, continuity into the dashboard, scoped campaign read, verified draft in a safe workspace and an inspectable trace. M2–M6 broaden and deepen capability on both surfaces. M7 moves the proven experience into the native frontend and WordPress so visitors install nothing. “Able to help with everything” is the product direction; each action is exposed as executable only after its own contract, authority and result check passes.

- On 30 September, the founder chose browser-first execution: through M6 the extension acts inside the user's own authenticated dashboard session (the same authority the user already has), so no account-wide MCP/API key enters the browser or this repo. Verification reads back the saved object through the dashboard itself. Existing MCP/API tools are recorded as a reference column in the capability map and are used only where the browser path cannot perform or verify an action (for example the unauthenticated website side in M7).

M1 therefore upgrades the existing extension across a website-to-dashboard journey through one bounded end-to-end capability slice, without installing a production embed. Map the dashboard capability surface (browser executor status plus the existing MCP tool, if any) so later capabilities have clear entry points; verify each action as it is added. Keep the reusable conversation, goal and tool logic independent of extension-only APIs where practical so a small WordPress script/iframe and native dashboard mount can reuse it in M7. Prefer in-session browser execution, then existing APIs/MCP, over deep changes to `sbl-app`; add a narrowly scoped server-side bridge only if neither can safely serve a requested action. Changes to other repositories require their own branch/PR and owner review; this specification does not move or replace the current branch.

## Functional requirements

- FR-1: Upgrade the existing extension so one concierge carries the visitor from `sbl.so` into the dashboard and can build and run a campaign end to end through the real dashboard (brief, leads, sender, messages, launch). Launch executes only after the explicit visible approval. M1 proof creates and reads back a `[CX-TEST]` campaign in the `Second Brain Labs - 02` workspace without launching it. A formal capability map is deferred. (T01)
- FR-2: Start with a small manually reviewed website/product/capability catalogue for the homepage, pricing, one representative landing page and the first app workflow; expand it as needed. Give answers source/freshness and availability labels. Obtain actionable pricing and eligibility from the dashboard/backend when that flow is introduced; public pricing is contextual, and promotions must actually exist. (T02)
- FR-3: Develop the branded animated SBL brain as a draggable bottom-center dock (rb2b-style) with conversation, live transcript and waveform in place, complete text interaction, voice (the concierge may ask the visitor to allow the microphone and point at the browser prompt; denial keeps text), progress/results, dismissal and accessible controls in the Chrome extension on both `sbl.so` and the actual SBL dashboard. In M7, deliver it through a small WordPress script or iframe entry point on sbl.so homepage and landing/pricing pages, plus a minimal JavaScript mount in app.secondbrainlabs.com where feasible; visitors install nothing. (T03)
- FR-4: Collect semantic page/section/click/exposure/active-time and permitted task events; maintain confirmed facts and resumable task context under session/account/workspace scope with an explicit cross-domain signup handoff. Distinguish agent actions, missing telemetry and visitor actions. (T04)
- FR-5: The model decides what to say and do from the full context (visitor story, surface, account state, conversation, SBL knowledge); no fixed scripts. Surface objectives steer it: website → signup; dashboard without a campaign → create one; with campaigns → optimize results and move to paid; trial ending → fastest results. Choose and revise discovery, conversion, activation, support, retention or expansion goals from explicit requests, behavior and verified state. Wait while visitors explore; open when behavior shows intent. Support requests override sales prompts; suppress interruptions after dismissal, during typing and in hidden tabs. (T05)
- FR-6: Start in M1 with a scoped, agreed campaign draft and verified readback in a safe workspace. By M4, carry the brief through the prototype's website-to-app journey, complete or reuse an existing draft, and explain remaining prerequisites without duplicating work. Verify the extension-free handoff in M7. (T06)
- FR-7: The model picks the lead route (ICP prompt, Sales Navigator, post engagement, signals, CSV) from context rather than a fixed path, then previews, confirms meaningful cost/effect, executes and verifies. (T07)
- FR-8: Read scoped campaign results, diagnose supported sender/setup issues, resume work and perform validated run/end/message/intervention actions after specific confirmation; verify actual outcomes and prepare useful human handoff when needed. (T08)
- FR-9: Record context-to-goal-to-tool-to-result traces, model/rule/source versions, latency/cost, action receipts and feedback from the first working slice; provide capability controls and a kill switch. Deferred by the founder until after the core capability milestones; then start with a local trace log and export to Langfuse once access is confirmed. (T09)
- FR-10: Spawn a bounded internal research worker for useful competitor/market/event questions; return source URLs, retrieval dates, uncertainty, conflicting findings and relevance. Cache/deduplicate, cancel and stop at budget; turn accepted recommendations into supported drafts. Research never authorizes consequential actions. (T10)
- FR-11: Add demanded workspace/CRM/knowledge/enrichment/billing/deletion actions only after verifying each contract. Ask for exact consequential-action confirmation, then execute and verify rather than categorically refusing. (T11)
- FR-12: Bind confirmation to a specific target/workspace/content/effect/quote; recheck authority and state, invalidate changed proposals, reconcile uncertain effects before retrying, and distinguish submitted/queued/delivered/completed.
- FR-13: Help new, returning and inactive customers with appropriate lifecycle journeys; refresh old state and allow goal correction. Absence does not establish churn, and a website script cannot reach an absent customer by itself.
- FR-14: Start indexing with a small reviewed catalogue and explicit coverage gaps. Rules plus the conversational model handle routing; Jev evaluation is deferred until traced routing failures justify it.

## Non-functional requirements

- NFR-1: Fresh-browser journeys require no extension or localhost. Verify desktop Chrome and Safari plus mobile Safari, keyboard navigation, reduced motion, mic denial and host usability on embed/model failure.
- NFR-2: Prevent cross-account/workspace context exposure; keep secrets server-side, mask trace payloads, avoid raw keystrokes/full contact dumps and private data in public searches, and respect capture and deletion controls. Test logout, workspace switch and identity handoff.
- NFR-3: Tracing failure must not freeze the product; preserve action receipts, alert on missing telemetry, enforce configured cost/time budgets and stop new actions through operator controls. Validate stale state, duplicate delivery and uncertain writes.
- NFR-4: Intent engine (the product's brain): build a live visitor context from entry source/referrer, page sequence across both domains, sections dwelled on, scroll depth, semantic clicks, visible/active time, return visits, device, what is currently in view, and what was seen but not clicked (exposure without interaction). The browser collects the raw signals locally (about every 1–2 s). A model (LLM now; Jev TypeSafe later if useful) infers intent, persona/role (e.g. agency), interests (e.g. profiles, numbers/trust, pricing) and concerns with a confidence and the evidence behind each, re-run when the raw signals change meaningfully, not per tick. Local rules serve only as change detection and the no-key fallback. Show the visitor why the concierge spoke ("pricing 38 s, viewed case study, returned to pricing"). Cursor/hover are attention proxies, never claimed gaze or definite intent. Mobile/keyboard users work without pointer data.
- NFR-5: Execute in the user's own session first, then reuse existing backend/datastore/tools before adding infrastructure; keep the eventual app integration to a small mount and use one bounded research worker. Add a narrow server-side adapter only for a demonstrated auth/action gap; browser fallback must be scoped and tested. Set latency/cost targets from the first working slice before cohort rollout.

## Constraints

- Frontend only: the concierge acts through the SBL website and dashboard UI in the user's own session and makes no changes to, or direct calls into, SBL's backend. Its only server is the existing local concierge session server, which holds the model key.

- Stay on feat/human-cursor-memory-and-endpoint-capture. Preserve existing changes and extension implementation. The WordPress site and production app/backend are outside this checkout; changes there need the owning deployment path and review.
- Current authorization is Genesis initialization and planning only. Specification and plan approvals must be real human decisions, not inferred from initialization.
- Specific consequential approvals are part of the product behavior; no live campaign, message, payment, deletion or deployment is authorized in this session.
- Use Genesis and official Ponytail full. Avoid speculative abstractions and a separate service per diagram box. Raw telemetry retention of 30 days is a proposal requiring owner confirmation; align audit retention with existing policy.
- Use the four knowns/unknowns categories and cheap design prototypes to resolve tacit taste. Preserve three outcome tracks: useful work/continued use, signup/demo conversion, support resolution.

## Non-goals

External-agent/A2A service; visitor Chrome extension; universal browser robot; actual eye tracking; continuous pointer-driven model calls; broad always-on market monitoring; autonomous unapproved campaign launches; speculative churn prediction; a new analytics platform; every product mutation at launch; second-SaaS commercialization before SBL proves the experience; Jev routing before evidence of need; MCP/API keys in the browser; SBL backend changes; desktop-wide screen-aware copilot, agent-to-agent layer and experimentation engine (later products built on this core).

## Acceptance criteria

- AC-1: Before M7 customer rollout, all approved end-to-end journeys have current-source proof, no critical open defects, required independent review, measured latency/cost, feature disable and rollback rehearsal. Report the three outcome tracks separately. (T12)
- AC-2: At the M7 gate, at least 20 reviewed website scenarios yield at least 90% useful grounded responses and zero invented pricing/availability promises; homepage, representative landing page and pricing have appropriate next steps.
- AC-3: At the M7 gate, at least 20 lifecycle transitions yield at least 90% appropriate objectives; all suppression/isolation cases pass and explicit support never receives a forced sales prompt.
- AC-4: At the M7 gate, at least 20 varied eligible draft attempts yield at least 90% verified completion with zero false-success claims; existing drafts, timeouts, duplicates and validation failures recover truthfully.
- AC-5: Consequential-action proof covers exact proposal, yes, authority/state recheck, execution and verification; changed targets invalidate approval and retries do not double-send or duplicate charged work.
- AC-6: Internal research proof covers relevant sources, stale/conflicting/no-evidence results, privacy, cancellation and budget stop; parent/child traces connect a useful recommendation to a verified requested draft.
- AC-7: Signup/return continuity and new/active/inactive/support cases work across the two surfaces; raw telemetry, task summaries, traces and authoritative action receipts have explicit storage, scope and deletion behavior.
- AC-8: Product failures, voice denial and tracing outage preserve usable host/text paths; each exposed capability has tested authority and recovery behavior. Unsupported capabilities are not advertised as executable.

Milestones M1–M6 prove their capability with smaller fixture sets that cover the named cases; the 20-scenario/90% thresholds in AC-2–AC-4 apply to the M7 pilot gate.

## Risks

This repository is an extension prototype; `sbl-app` is the current dashboard/backend deployment home, and the founder owns the WordPress deployment. Confirm app review/access before integrating there. Documented MCP/API operations can have billable or sending side effects; validate each in a safe test workspace before exposing it. Behavior is ambiguous: use hypotheses and clarification, not mind-reading. Stale pricing/research misleads: require current authority and sources. Research can become costly noise: bound it and evaluate relevance. Early pilot samples reveal usability, not proven conversion lift.
