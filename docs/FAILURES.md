# Failure paths (FR-6, FR-14, NFR-13, AC-7)

Rule: a failure never leaves the visitor with silence. Every row ends the turn with one honest line, or with a visible, correct state. Strings are in `harness.js` (`UNAVAILABLE`, `CAPPED`, `STUCK`, `NOT_OPENED`, `BUDGET_LINE`) and `core/turn.js` (`FALLBACK`).

How the page learns why a model call failed: `content.js:routeCall` resolves to `{ failed: "unavailable" | "capped" | "down" }` (classified by `core/router.js:failure` from the server's status and code), or `null` when the model answered but gave no usable route.

## Fault injection

Start the server with `ALLOW_FAULTS=1` (off by default; without it the header is ignored). The page sends `X-SBL-Fault: unavailable | capped | down | slow` on `/agent/route`, `/agent/chat` and `/agent/note` only when proof mode is on and `sessionStorage.sbl_fault` is set. The server answers as that failure would (403 + code, 429 + `visitor_cap`, 502, or a 10 s delay then 504) without calling upstream. `node tools/experience/run.mjs --set faults` runs the `faults` persona; `node tools/experience/gate.mjs faults` passes on 0 silent turns, 0 `E8.late`, 0 `honest` misses and 0 unrequested navigations (exit 1, with a message, when no faults run exists).

## Deviations

- The engine-opened turn after a router `down` gets a 9 s watchdog (`limits.downWatchdog`), not 25 s. A healthy engine that needs more than 9 s to speak after a failed router call is cut off with the unavailable line.
- `failures` (consecutive failed model calls) is not reset per turn; a stale value makes a later watchdog say "unavailable" instead of the generic line until the next successful model call.

- Item 5: tc17 tested a 3.5 s silent-router deadline and measured a 12.521 s slow-fault reply. The combined candidate failed the no-worse comparison; the deadline was restored to 7 s for the narrower tc18 candidate.
